Design patterns → implementation

Factory — order types

OrderFactory.create(type, payload) returns a MarketOrder, LimitOrder, or StopLossOrder instance. Each implements .validate(balance, holdings) and .toKafkaPayload(). Adding a new order type = one new class + factory registration.

Observer — price events

Redis Pub/Sub channel price_channel is the event bus. WS fan-out and limit-order checker are independent subscribers. Neither knows about the other — pure observer decoupling.

Strategy — sim engine

Python sim accepts a strategy config: random_walk, mean_reversion, circuit_breaker. Each is a class implementing next_price(current: float) → float. Admin can hot-swap strategy via Kafka control topic.

Command — trade commands

Each Kafka order message is a serialized command object with an idempotency key (order_id UUID). The order engine can replay Kafka from offset without double-executing, enabling crash recovery.

Consumer group design

price-persister group

Reads price.ticks. Batch-inserts into TimescaleDB every 500ms using a buffer. Avoids per-tick DB writes at high simulation frequency. Also updates Redis HASH and publishes to Redis Pub/Sub.

order-engine group

Reads orders.placed. Processes exactly-once via idempotency check on order_id in DB. Executes trade, updates balance + holdings in a single DB transaction, then emits to orders.filled.

Data structures
HASH prices
Key: prices. Field: ticker. Value: JSON {price, ts}. TTL 5s per update. GET /stocks reads from here — never hits DB for current price.
ZSET pending_limits
Key: limits:{ticker}. Score = limit_price. On each tick, ZRANGEBYSCORE finds triggered orders. O(log n + k) — very fast.
STRING session:{token}
Blacklisted JWTs after logout. TTL = remaining JWT lifetime. Checked before processing any authenticated request.
PUB/SUB price_channel
Elysia publishes each tick here after DB insert. All WS handler threads subscribe and fan-out to connected clients.
HASH leaderboard:{id}
Competition leaderboard cache. Refreshed on orders.filled events. Served directly to client without DB join. TTL 30s as fallback.
Limit order trigger logic
// In price.ticks Kafka consumer — runs on every price update async function checkLimitOrders(ticker: string, currentPrice: number) { // Buy limits: trigger when price drops to or below limit_price const buyHits = await redis.zrangebyscore(`limits:buy:{ticker}`, '-inf', currentPrice) // Stop-loss / sell limits: trigger when price rises to or above limit_price const sellHits = await redis.zrangebyscore(`limits:sell:{ticker}`, currentPrice, '+inf') for (const orderId of [...buyHits, ...sellHits]) { await kafka.send('orders.placed', { orderId, triggeredAt: currentPrice }) await redis.zrem(`limits:buy:{ticker}`, orderId) } }
Tech: Python microservice using confluent-kafka-python. Runs independently of the Bun backend. Controlled via sim.control Kafka topic.
Architecture

Strategy classes

  • RandomWalkStrategy — Gaussian noise applied each tick. Configurable σ (volatility) and drift.
  • MeanReversionStrategy — Price drifts back toward a set mean. Models stable stocks.
  • CircuitBreakerStrategy — Clamps price movement to ±X% per tick. Admin-triggerable.
  • UserInfluenceStrategy — Wraps any base strategy; adjusts price based on recent buy/sell volume from DB.

Tick loop

# sim/engine.py while running: for ticker in tickers: price = strategy.next_price(prices[ticker]) prices[ticker] = price producer.produce('price.ticks', { 'ticker': ticker, 'price': price, 'volume': random_volume(), 'ts': time.time() }) time.sleep(tick_interval) # e.g. 1.0s
User volume influence

Every N ticks, the sim engine queries the DB (or reads a Kafka compacted topic) for recent buy/sell volume per ticker. Net buy pressure pushes price up; net sell pressure pushes it down. This creates the authentic supply-demand feel required by the spec.


price_impact = (net_buy_vol - net_sell_vol) / total_vol * impact_factor new_price = base_price * (1 + random_walk_delta + price_impact)
